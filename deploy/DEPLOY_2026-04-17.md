# Deploy checklist — cleaned-dataset + toggle + feedback inbox
_Prepared 2026-04-17 — execute in order. Everything local is verified green._

Everything before this patch: backend serves the raw UHRI export only.
After this patch: backend serves the cleaned dataset by default, supports
`?dataset=raw` for the legacy view, and accepts feedback via
`POST /api/feedback/report`. Frontend gets a visible header toggle
(Cleaned / Original UHRI) and a bilingual "Report a cleanup error" flow.

The SQLite schema is bumped to version 2 via a `schema_version` meta
row; the API automatically rebuilds the DB on the first request after
deploy. No manual migration, no data loss.

## Rollback

If the deploy goes wrong:

1. Reverse the env override: `sudo systemctl edit --full uhri-api` →
   remove the `UHRI_CLEANED_PATH` line → `systemctl restart uhri-api`.
   The API falls back to raw-only behaviour (no cleaned data, no
   section headings in search). The frontend toggle still works but
   behaves as a no-op since the server ignores `?dataset=raw` the
   same way it now ignores `?dataset=cleaned`.

2. Reverse the code: `rsync` the previous `unhr_dataset_api.py` back
   from your backup or git history, delete the stale SQLite,
   `systemctl restart uhri-api`. The schema-version meta check will
   force a rebuild into the old schema.

3. Frontend: revert the last three files via `git revert` or
   redeploy the previous gh-pages commit.
